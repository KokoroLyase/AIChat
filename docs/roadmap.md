## 一、总体原则

1. **先底座，后功能。** 0.4.0、0.4.1 已完成分页、崩溃日志、存储清理和导出保护；0.4.2 先补齐聊天信息、联系人资料和“我”页的界面逻辑，0.5.0 再做消息管线和全局内容。
2. **先做被依赖的，后做依赖别人的。** 0.5.0 的节奏和可靠投递先于 0.6.0 主动聊天、0.7.0 语音消息和 0.8.0 语音通话。
3. **独立且高风险的大模块放后面。** 语音消息和语音通话要对接外部 TTS/ASR 服务商，不确定性最高，排在 0.7.0、0.8.0。
4. **叶子功能灵活安排。** 多选、收藏、引用、翻译、图标和动画没有别的功能依赖，集中放在 0.9.0。
5. **升级后的默认行为按版本区分，不再统一套用旧规则。**
   - 0.4.2 的免打扰默认关、聊天背景默认无，已有联系人的行为和费用不变。
   - **0.5.0 的全局记忆和回复偏好对新联系人和已有联系人都默认开启**（用户 2026-11-07 决定）。这会改变已有联系人的请求内容、费用和说话方式，更新说明必须写明；不要以“升级不能变贵”为由改回默认关闭。
   - 0.6.0 主动聊天默认关闭，必须由用户手动开启。
   - 0.7.0、0.8.0 的语音由用户主动使用，不自动发起。
6. **会自动花钱的功能默认关闭。** 没有用户操作就调用模型的功能，都要有开关、额度、用量归类和可见的运行状态。
7. **数据迁移和备份同步。** 改表必须写迁移，改数据格式必须升备份版本；新表、新字段、新设置和新媒体目录都要纳入导出与恢复。

## 四、贯穿每个版本的开发规则

1. **数据库迁移。** 改表必须版本 +1、写 Migration、用 `app/schemas` 做迁移测试，禁止 `fallbackToDestructiveMigration`。数据只在本机，迁移失败就等于数据丢失。
2. **导出/恢复同步更新。** 新表、新字段、新设置和新媒体目录都要纳入。改 `data.json` 时 `BackupFormat.VERSION` +1 并补迁移。
   - 合并恢复时联系人 id 会变，新表里指向联系人的字段都要重新映射。
   - 新媒体目录要加进 `BackupFormat.mediaNamePattern`，否则恢复时会被当成非法路径。
   - 应随备份走的设置放进 `SettingsDto`，与设备有关的状态（如今日额度）不导出。
3. **文字资源。** 界面文字一律写进 strings.xml。Android lint 的 `HardcodedText` 不能替代 Compose 资源检查；沿用已有 `StringResourceGuardTest` 和基线，只减旧例外，不给新功能新增白名单。
4. **隐私说明草稿。** 每新增一个要连接的服务器或一类本地数据，就在 `docs/privacy-draft.md` 记一笔，1.0.0 时定稿。
5. **新页面图标。** 新页面需要的图标直接按 `WeIcons` 的自绘线性风格画，不新增图标依赖。
6. **日志脱敏。** 任何日志都不得记录 API Key、消息正文、记忆、提示词和图片内容。**异常的 message 也算日志**，可能带着服务商返回内容或 URL，默认不写入崩溃日志。
7. **新消息类型或状态的检查清单。** 新增 `MessageType` 或 `MessageStatus` 时，逐项确认：列表显示、会话预览、未读、通知、搜索、上下文拼装、记忆总结、用量、删除和清空（含文件）、重试和重新生成、导出和恢复。
8. **自动调用模型的测试。** 只用本机模拟接口。真实服务商调用先问用户，debug 包里不放真实 Key 做调度测试。

**状态**：2026-11-09 发布，tag `v0.5.0`（`main` `67751e1`）。在 `feature/0.5.0`（从 `main` `a2449ae` 出发）开发和验证，CI 通过后合并到 `main`。正式 APK 6,919,884 字节，SHA-256 `8abd65bdf91a40dd75c99b14176299d5b3d06283f286e0be7f91249dc0d1d8b7`，与 `.sha256` 一致，包名、版本 0.5.0 / 500 和签名证书（与此前各版相同）已核对，CI 产物 `mapping-0.5.0` 已生成；分支 CI、`main` CI 和 Release 工作流一次通过。分批提交：`de15140` 版本号、`078fb2a` 数据与兼容、`99d3d46` 0.4.2 请求基准、`147d803` 全局内容与预算、`e707a9c` 回复偏好、`d6de5e5` 可靠投递（单独提交）、`0dfb2f5` 非 ASCII Key 修复、`db0e45c` 0.4.2 备份夹具、`3dfccd8` 模拟接口、`087410c` 文档；真机验证中发现并修复两处投递问题：`0d5bbaa` 投递任务转前台、`d0e3eea` 启动恢复替换旧投递任务；`3e30383` 补记验证结果。之后按用户要求追加：`c6889a3` 模型不换行时按句末断句兜底、`6530f20` 投递只在还要等时转前台、`33c5c8b` 覆盖恢复前选择是否保留本机全局记忆，以及文档提交；用户用 perf 包实测通过后，`90ebd5e` 按用户调好的值改了回复偏好默认值；发布前全面核对了文档。下面先记录实际结果，原计划保留在后面供对照。

**实际完成：**

- **数据：** 全局记忆三张表（类别、主题、条目，删除类别/主题级联），`Contact` 增加 `useGlobalMemory`、`useReplyPreferences`（库默认 1）；Room v4→v5（`MIGRATION_4_5`、schema 5）；回复偏好存 MMKV。备份内层 v4→v5：导出全局记忆、回复偏好和两个开关；`v4ToV5` 让旧备份的联系人两项都开启，`splitReplies`、免打扰、聊天背景照旧。
- **全局记忆：** 我 → 全局记忆 → 类别 → 主题 → 条目，各自一页；条目可单独开关、编辑、删除，三层都能调整顺序；删除有内容的类别或主题先确认（级联删除）。总览页写明会发给哪些服务商、条数、字数和按汉字 1 token 估算的占用，可一键让全部联系人开启或关闭。
- **回复偏好：** 我 → 回复偏好，一页加减调整：稍等秒数（默认 1）、每条字数（16）、每轮条数（1～3）、间隔（2～4 秒）、去句尾标点（开）；也可一键让全部联系人开启或关闭。
- **提示词与预算：** 只在 `ContextBuilder.systemPrompt` 组装，顺序为全局记忆 → 人设 → 记忆 → 回复方式 → 时间和昵称；记忆总结、合并请求不带这两项。联系人编辑页新增两个开关，“系统提示词”一行下显示合计占用，超过上下文上限一半时提醒（提示词页同样显示）。
- **回复节奏：** `ReplyRhythm` 按任意换行拆条、去空行；模型没换行、某条超过每条字数两倍时在句末断开再合并短句（不在逗号处拆，有代码块不拆）；超过条数时多余部分接在最后一条、只去“。”“，”；间隔按每字 300 ms 加 0～1500 ms 随机，限制在设定范围，第一条扣掉生成用时。等待在 Worker 内用可取消的 `Sleeper`，时钟和随机数可注入。关闭回复偏好时走原 `splitReplies` 逻辑。
- **可靠投递：** `MessageStatus.PENDING`；`ReplyEngine` 一个事务写入全部待投递条目后排 `deliver-{contactId}`（APPEND_OR_REPLACE，与 `reply-` 分开）；`DeliveryEngine` 到点逐条转 SUCCESS，转时才更新预览、未读和通知（通过 `ReplyAlerts`，同一组只第一条响铃，免打扰照旧不发）；`ReplyEngine.run` 先送完已生成的再请求模型；启动时 `recover()` 送达到期的、重新排未到期的。分页、搜索、搜索定位计数、新消息计数、未读锚点、预览、记忆 `planBatch` 都排除 PENDING；导出按已送达写入；删除聊天、清空、删除联系人、恢复都取消投递任务。
- **修复（用户 2026-11-09 同意随 0.5.0）：** Key 含 0x21～0x7E 以外的字符时，请求前就报“Key 无效”（`LlmException.INVALID_KEY`），消息标为发送失败可重试；`ReplyEngine`/`ReplyWorker` 兜底意外异常，不再一直“正在输入”；服务商编辑页拒绝保存这样的 Key。
- **版本与文档：** 0.5.0 / 500；`docs/release-notes/v0.5.0.md`（写明默认开启会改变已有联系人的请求内容、费用和说话方式）、README、设计方案、隐私草稿和本文已更新。

**实现时的决定（向用户报告）：**

- “我”页把两个入口放成单独一组，位于个人卡片和四个设置入口之间。
- 覆盖恢复前，本机有全局记忆时由用户选择保留本机的还是用备份里的（0.4.2 及更早的备份没有全局记忆，这时是保留或清空；用户 2026-11-09 要求）；合并按创建时间认同一个类别、主题，保留本机名称和顺序，同一主题下内容相同的条目不重复。回复偏好覆盖时用备份里的，备份没有或合并时保留本机的。
- 免打扰仍只抑制回复通知，投递的通知也一样。

以下为原计划（2026-11-07），保留供对照：

**目标**：让联系人共享用户手写的全局记忆，按用户设定的回复偏好像真人一样分条、带间隔地回复，并把回复从“写库即显示”改成可靠的待投递管线。这一版的核心是消息管线，不只是“我”页多两个入口。

**本版范围：** 全局记忆、回复偏好、可靠投递。**不包含**全局指令/人格准则（用户 2026-11-07 决定不再加入）、主动聊天、朋友圈、语音、数据库加密。自动提取所需全局记忆是“如果可行”的目标，不是阻塞项。

**1. 全局记忆**

- 入口：我 → 全局记忆。用户可以添加多个大类别，进入类别后添加主题，在主题下填写具体记忆信息。
- 每条记忆可以单独启用、编辑、删除；类别、主题、条目都支持排序；显示总字数和大致 token。token 估算按现有 `TokenEstimator`，跨服务商按较高值显示（DeepSeek 汉字 0.6，其他 1；用 1 更保守）。
- 删除非空类别或主题时，先确认是级联删除还是要求先清空；不能静默丢数据。
- 和所有联系人聊天时都能读取；用联系人级开关控制是否使用，默认开启。
- **必须明确提示：这些内容会发给每个开启它的联系人所用的服务商。** 全局记忆会被多个联系人复用，可能发给不同服务商，不能悄悄开启。
- 自动提取是“如果可行”的目标。优先本地判断（类别、主题、关键词、最近消息），不额外调用模型；如果必须额外调用模型才能判断，先报告方案和费用，不擅自实施。做不到可靠选择时，默认发送全部已启用条目，并在报告中说明。如果实现了自动提取，默认开启并提供关闭选项，不能因此悄悄增加模型调用或费用。
- 数据：全局记忆需要类别、主题、条目三类数据，纳入备份；合并恢复时按现有原则处理，若现有原则覆盖不了再提出实质问题。

**2. 回复偏好**

- 入口：我 → 回复偏好，默认预置：
  - 用户发送消息后，联系人稍等 3 秒，确认用户没有再发新消息，再开始回复。
  - 每条回复长度保持在 14 字左右。
  - 每轮连续发送 1～5 条消息。
  - 回复默认不带句尾标点。
  - 回复消息之间的间隔为 3～10 秒。
- 这些是全局默认值，界面上可调整；联系人级至少提供“使用全局回复偏好”的开关，默认开启。新计划没有要求联系人逐项自定义覆盖，不要自行扩大范围。
- 字数和条数写进提示词作为风格引导；“用换行分隔每一条”是 App 和模型之间的协议，放在 App 生成的回复偏好要求里，不放在用户可编辑文本里。
- 标点由 App 处理：默认去掉句尾标点。约定细则是只去“。”和“，”，保留“？”“！”“…”；新计划没有改这条细则，用户 2026-11-07 已确认按此执行，存的就是显示的内容。
- 回复偏好开启时按任意换行拆条，去掉空行；超过条数上限时把多余尾部合并进最后一条；字数不做硬截断。
- 回复偏好关闭时保留旧 `splitReplies` 行为：原先开启的仍按空行拆、约 1 秒依次显示；原先关闭的仍为一条。
- 间隔按字数估算打字时长加少量随机，限制在设定范围内；第一条的等待要扣掉模型已经用掉的时间。时钟和随机数可注入，便于测试。
- 3 秒等待要可注入、可测试，不要在主线程 sleep；注意 WorkManager expedited 任务和 initial delay 的兼容，必要时在 Worker 内用可取消的 delay。

**3. 可靠投递**

- 新增 `MessageStatus.PENDING`。模型返回后在一个事务里写入全部消息，`createdAt` 是计划时间，用状态区分是否真正投递。
- 只有转为 SUCCESS 时才更新会话预览、未读数和通知；现在是写库时一次完成，会提前剧透。
- 投递放在单独的唯一任务 `deliver-{contactId}`，不能放在 `reply-{contactId}` 里，否则用户一发消息，REPLACE 就把投递也取消了。
- App 被杀后：启动时把到期的 PENDING 转为 SUCCESS，未到期的重新排队；`markInterruptedRequests` 不能把它们标成失败；任务重试时（`runAttemptCount > 0`）继续投递，不按失败处理。
- 同一联系人的通知随投递更新，不要每条都响一次；“对方正在输入…”在等待回复或有 PENDING 时显示。
- 模型还没返回时，保持现有规则：取消旧请求，一起回。投递期间又发消息：已生成的继续发完，新请求排在后面；`ReplyEngine.run` 要等 PENDING 全部投递后才开始。
- 用户消息的时间会夹在几条回复中间；拼接上下文时要把等待回复的用户消息排到最后，保证发给模型的最后一条是用户消息。这一点要有回归测试。
- 用户点“取消”只取消还没生成的请求，不撤回 PENDING；删除聊天、清空、恢复要取消投递任务。
- 按第四节第 7 条逐项检查所有读消息的地方：搜索不能搜到 PENDING，搜索定位的计数也必须使用相同可见范围；`ChatPaging` 的 `timeline/entry`、`latestVisible`、新消息计数、未读锚点、`ChatMessageActions` 的重试和重新生成都要核对；每次 PENDING 转 SUCCESS 会刷新 Room/Paging，必须保留 0.4.1 的静止历史锚点修复，并覆盖远处历史、手指拖动、惯性滑动和新消息浮标；记忆的 `planBatch` 要排除 PENDING；导出时 PENDING 按已送达写入，恢复后不会再次投递；聊天列表预览、重新生成在 PENDING 时禁用。

**4. 升级后的默认值**

- **新功能对新联系人和之前已有的联系人都默认开启**（用户 2026-11-07 决定）。这会改变已有联系人的请求内容、费用和说话方式；更新说明必须写明，不要以“升级不能变贵”为由改回默认关闭。
- 旧 `splitReplies` 字段保留用于数据兼容；回复偏好开启时不再由它决定拆条；关闭回复偏好时回退到它的原行为。

**5. 提示词与预算**

- 组装顺序：全局记忆 → 联系人人设 → 联系人记忆 → 回复偏好要求 → 当前时间和昵称。没有全局人格准则。
- 全部为空时维持现有行为，不发送系统提示词。只改 `ContextBuilder.systemPrompt` 一处；`MemoryEngine.historyBudget` 也调用它，触发阈值才会一致。
- 记忆总结和合并的请求不注入全局记忆和回复偏好要求，保留原总结/合并指令，不因全局文本增加这些请求的输入 token。
- 全局内容算进联系人的上下文预算。默认 4000，最小 1000；系统提示词太长时 `historyBudget` 会变成负数，聊天记录被丢光，记忆也会反复触发（有 200 的下限保护）。不新增预算字段，不改 80%、1/4 的规则。
- 全局页和联系人编辑页显示占用；系统提示词超过联系人预算一半时，在联系人编辑页提示。0.4.2 起提示词在单独的“系统提示词”页编辑，这个提示要放在编辑页的提示词一行或提示词页上，保证编辑时能看到。极端长内容要有测试。

**数据与迁移：**

**目标**：开启该功能的联系人根据时间和聊天状态主动来找用户。复用 0.5.0 的待投递机制；本版建立调度器和每日额度。这是第一个没有用户操作就花钱的功能，所以默认关闭，状态要看得见。

**1. 后台调度**

- WorkManager 周期任务，最小间隔 15 分钟，需要联网。只在至少一个联系人开启时才注册。
- 不用精确闹钟，不申请额外权限。App 回到前台时也检查一次（`lifecycle-process` 已有依赖）。
- **要接受的现实：** Android 的周期任务不准时，小米 HyperOS 还可能在划掉后台或省电时不执行，强制停止后要等下次打开才恢复。不能把“一定按时到”作为目标。“我 → 通用设置”引导去关电池优化（已有入口）和开自启动，并显示最近运行时间。

**2. 触发逻辑**

- 对每个开启的联系人算触发概率：距上次互动、当前时段、频率设置。写成纯函数，时钟和随机数可注入。
- 触发判断还要考虑用户是否发送过带有时间、时刻的相关请求。
- 这些情况直接跳过，不调模型：免打扰时段、今日额度用完、连续未回复已暂停、正在等回复或有 PENDING、用户此刻正在看这个聊天、配置校验不通过（`ModelRules.validate`）、没有 Key。
- 可能触发后调模型：人设、全局记忆、联系人记忆、最近聊天、当前时间，并说明“如果现在不想找对方，只输出 [SKIP]”。
- **请求结构：** 主动请求没有新的用户消息，历史可能以助手消息结束，甚至为空。要追加一条临时的 user 角色指令，只在这次请求里，不存库。
- **[SKIP] 判断要宽：** 去掉空白和标点后含有 SKIP 就不发。把 [SKIP] 显示给用户，比少发一条严重得多。
- 额度**在发请求前**扣减，[SKIP] 和失败都算。失败不重试，不通知。

**3. 设置项**

- 联系人级：
  - 主动聊天总开关：关闭 / 开启，默认关闭；
  - 主动发送频率：偶尔 / 适中 / 频繁，默认适中。
- 全局：
  - 免打扰时段，默认 23:00～7:00（要处理跨午夜）；
  - 每日主动调用上限，默认 20 次；按本地日期重置。
- 防刷屏：默认单次主动发送连续发 2 条后，若用户没有回复则本次暂停；用户再次发言后恢复。
- 第一次开启时：申请通知权限（现在是第一次发消息时才申请，可能已被拒），并说明会自动消耗 API 额度。
- 状态显示：今日已用、最近运行时间、每个联系人是否暂停及原因。没有这些，用户无法区分“没触发”和“被系统杀了”。
- 用量统计不单独设置，合入“我” → “模型服务” → “用量统计”。

**4. 消息和投递**

- 主动消息走 0.5.0 的回复偏好和投递，可以分多条，发系统通知，点击进入聊天（已有）。
- `Message` 加来源字段（普通回复 / 主动）。
- **主动消息不能“重新生成”。** 现有 `regenerate()` 删掉最后一轮回复后，会把前面的用户消息重发；没有用户消息时任务直接结束，这条主动消息就丢了。
- 记忆总结、上下文照常包含主动消息。现有逻辑会去掉开头的助手消息，主动消息不受影响；连续两轮助手消息会合并，要有测试。
- 用量新增 PROACTIVE 分类，但合入现有用量统计页，不新增独立统计入口。

**数据：** Room +1（来源字段、联系人设置、会话的暂停状态、每日额度）；备份 +1。每日额度和暂停计数不随备份恢复。

**测试：** 只用模拟接口。debug 包提供“立即运行一次”。真机只用 debug 包，真实服务商的主动聊天先问用户。

**验收标准：**

- 开启后用模拟接口能收到主动消息，分条、有通知、可点进聊天；
- 免打扰（含跨午夜）不调用模型；到达每日上限后不再调用，次日恢复；
- 连续 2 条主动消息没有回复会暂停，用户回复后恢复；
- [SKIP] 不显示但计入额度；
- 主动消息没有“重新生成”，重试不会出错；
- 默认状态下没有任何后台模型调用；
- 真机杀进程、重启后的表现如实记录，不把 HyperOS 限制写成通过。

**1. 自动记忆提炼重点（用户的要求：自动生成的记忆要总结出重要内容，不然占的上下文太长，还会影响模型注意力）**

- 问题：0.7.1 的记忆最多占上下文上限的 1/4，上下文开到 128k 时要积累到约 3.2 万字才开始合并；每批聊天都生成一条（寒暄也是），合并出来仍是按时间的流水账。
- 做法（推荐，用户同意）：记忆分两层。**核心记忆**每个联系人一条，记着现在仍然成立的重要事实（不超过约 500 字）；**近期记忆**是按时间的一段段总结。每次请求先带核心记忆，再带最新的近期记忆，合计最多约 1500 token（上下文较小时最多占 1/4），不再随上下文上限增长。近期记忆超出约 800 token 时，把最早的、没改过的几条和核心记忆一起交给模型，输出更新后的核心记忆（多一次请求）。总结只记重要内容，这段没有值得记的回答“无”，不生成记忆、只推进进度。
- 用户改过的核心记忆之后仍会被模型整理（提示词要求保留没被新聊天推翻的内容）；改过的近期记忆不整理进核心记忆。升级前积累的长记忆在之后的回复里自动陆续整理（每次最多 6000 token）。

### 0.8.0 语音通话

**状态**：开发中。用户 2026-11-12（0.7.2 发布后）给出开工要求；开工前把实现上要定的 8 个问题整理成推荐方案，用户同意“按推荐开工”。在 `feature/0.8.0`（从 `main` 出发）开发，版本 0.8.0 / 800。本小节按桌面《智信 AIChat 更新计划.md》的 0.8.0 和当天的讨论结论改写；原来“复用 0.7.0 的 TTS/ASR、VAD 开工时定”的旧口径作废。通话由用户主动发起，App 不自动发起。

**目标**：在语音消息的基础上实现语音通话：自动判断用户说完一段话，识别成文字发给联系人，联系人的回复合成后播放，再接着听；通话不新开上下文，音频和文字都保留，聊天里显示为通话消息。

**1. 入口**

- 联系人详情“发消息”一栏下方加“语音通话”一栏；聊天页“+”面板“相册”“拍照”后面加“语音通话”。
- 发起前检查这个联系人实际的语音识别、语音合成来源（`VoiceRepository.sourceFor`，0.7.2 的规则）和大语言模型的 Key，有一样用不了就不能通话，弹窗说明原因，按钮去联系人资料或「我 → 语音消息」；**单独选的来源用不了时不换成全局的**。本机来源（系统语音合成、离线识别）照常可用。
- 这个联系人正在等回复（还没生成）时提示“对方正在回复，稍后再打”；已经生成、等着送达的回复在通话开始时立刻送达。
- 第一次通话前弹一次说明：录音发给哪个识别来源、回复文字发给哪个合成来源（本机来源写明不离开手机）、每轮都会请求模型、通话期间麦克风一直开着、切到后台也继续。然后申请 `RECORD_AUDIO`，拒绝后说明并给出系统设置入口。

**2. 判断说话和说完（VAD）**

- 用 sherpa-onnx（已随安装包）里的 Silero VAD。模型用 k2-fsa 导出的 `silero_vad.onnx`（约 629 KB，MIT 许可，Silero Team），**随安装包、不在手机上下载**：构建时和 sherpa-onnx 的 AAR 一样从官方 GitHub Release 下载、按写死的 SHA-256 核对后放进 assets，仓库不提交二进制；“开源许可”里注明。TEN VAD 的许可是改过的 Apache 2.0、官方提醒商用前看许可，不用。
- 参数：门限 0.5；说话短于 0.3 秒的不算一句（咳嗽、碰麦），不发去识别；静音 0.8 秒算说完，说完后 0.8 秒内又开口接在同一句里；一句最长 25 秒强制切开（智谱识别单次上限 30 秒）。sherpa 的默认值（最长 5 秒、静音 0.25 秒）都要改。
- 通话页在“在听”时有“说完了”按钮，可以手动立刻发出（环境吵、一直判断在说话时用）；也可以点静音。
- 手机跑不了 sherpa-onnx（非 arm64、原生库加载失败）时改用按音量的简单判断，同一个接口；JVM 测试用假实现和预置音频。
- 录音模块改成逐帧取样；只保存说话的那几段（前后各补约 0.3 秒），不保存中间的静音和背景声。

**3. 一轮的流程和延迟**

- 半双工：联系人说话时麦克风不送给 VAD。一轮 = 判断说完 → 识别 → 请求模型 → 合成 → 播放 → 回到“在听”。
- **按句流水线**：模型回复按流式接收，凑满一句（句末标点或换行，不太短）就送去合成；第一句合成好马上播，播放的同时合成下一句，句子之间隔约 0.3 秒。8 家合成和系统语音都适用，不改各家的请求格式。
- **不做**各家的流式合成（MiMo pcm16、火山、百炼 SSE、MiniMax 只有 4 家有，要另写 PCM 流式播放和逐家解析）和实时识别（百炼、火山是 WebSocket 加各自的协议）；VAD 切出的一句很短，整段识别即可。perf 包里按段记录每轮耗时（判断说完、识别、模型首字、首句合成、首次出声），只在 debug、perf 包写日志、不记内容；数字不理想再决定以后要不要做流式合成。
- 等待时通话页按阶段显示“正在识别…”“对方在想…”（带秒数）“对方在说”。联系人开着思考时，通话页顶部一行小字提示每轮可能要等较久、可以在联系人资料里关掉，不自动改配置。
- **打断**：不做“一开口就停止播放”（不戴耳机时联系人的声音会被录进去，回声消除看机型）。“对方在说”时显示“打断”按钮：立刻停止播放，丢掉还没放的句子，回到“在听”；只有已经放出来的句子（含被打断的那句）记进通话记录和上下文。

**4. 通话里联系人怎么回复**

- 回复偏好的等待时间在通话里不用（VAD 已判断说完），打字间隔不用；拆条的结果只用来分句合成，不拆成聊天消息。回复偏好的条数、字数要求照常带上（经 `ReplyPreferencesSource.forContact`），通话中和通话外拼接历史的方式一致。
- **通话中的请求**在系统提示词里多一段说明（放在“约定时间的写法”之后、时间和昵称之前，写在 `strings.xml`）：现在是语音通话，对方的话是语音识别转的文字、可能有错字，你的回复会被朗读出来，像打电话一样口语、简短，不用表情、括号里的动作、列表或 Markdown。**不在通话时没有这一段，请求和 0.7.2 逐字一致。**
- 约定提醒的标记照常解析（开启主动聊天的联系人在通话里也能约时间）。

**5. 通话消息和每一条的存储**

- 新消息类型 `MessageType.CALL`：用户发起，显示在右边；总时长复用 `voiceMillis`。通话进行中用单独的标记（不能用 SENDING / PENDING，会触发“正在输入”和投递）；App 被杀后启动时按最后一条的结束时间补完。
- 新表 `call_turn`：所属消息（级联删除）、序号、说话方、文字、音频文件、在整通里的起止时间、状态（正常 / 识别失败 / 合成失败 / 被打断）。一行是一“条”：用户说的一句话，或联系人回复的一句话。每句本来就分开录、分开合成，文字和音频一一对应，不用事后切分。
- 上下文、记忆总结、搜索都按条展开：用户的话按 user、联系人的话按 assistant，放在这条通话消息的位置。
- 音频在 `files/calls/`：用户的话识别后压成 AAC，联系人的话按合成返回的格式保存（WAV 同样压成 AAC）。
- **完整通话的音频不生成整段文件**：详情页“播放完整通话”按顺序接着放各条，每条之间留约 0.3 秒，进度条按各条时长累加、可以拖到任意位置（2026-11-13 实机验证后改，之前只能拖到某一条的开头）。
- 聊天里的通话消息显示通话图标和总时长，点进去是详情页：完整的每条文字，可以播放整通和每一条。

**6. 通话页、后台和中断**

- 通话页：头像、名称、计时、状态、最近一句的字幕（默认显示，可以收起）；静音、挂断、免提和听筒；“说完了”“打断”按上面的规则出现。默认听筒（`MODE_IN_COMMUNICATION`、`USAGE_VOICE_COMMUNICATION`），录音来源用 `VOICE_COMMUNICATION`，机型自带的回声消除和降噪能用就用。
- **锁屏和切到后台时继续**：通话开始时（页面在前台）启动 `microphone|mediaPlayback` 类型的前台服务（新权限 `FOREGROUND_SERVICE_MICROPHONE`；麦克风受“使用期间”限制，App 在后台时不能启动这种服务），通知写“正在和 X 通话”和“挂断”。挂断后录音、播放、前台服务和请求都不残留。
- 音频焦点：永久失去（如来电）时挂断，记录里写明原因；暂时失去时暂停听和放，拿回焦点后继续。不申请读取电话状态的权限。
- 失败：识别、模型、合成失败或断网时提示，回到“在听”，不自动重试（每次都花钱），用户再说一遍即可；识别失败的那句保留音频、文字标“识别失败”。**连续 3 轮失败自动挂断。**
- 保护：单次通话最长 60 分钟（55 分钟时提示）；5 分钟没人说话自动挂断（防止忘了挂、麦克风一直开着）。

**7. 和已有功能的关系**

- 通话中主动聊天跳过这个联系人（和“正在看这个聊天”一样），也不发这个联系人的回复通知。
- 挂断时取消进行中的识别、模型、合成请求，已得到的保留，没识别出文字的录音不保存。
- 用量分别计入现有的聊天、语音合成、语音识别，不单列“通话”。
- 通话消息可以删除（连同音频），不能重新生成、没有重试；聊天列表和通知显示“[通话]”加时长，搜索结果标“[通话]”。
- 删除通话、清空聊天、删除聊天和联系人、清空所有聊天记录都删掉 `files/calls/` 里对应的文件；存储空间单列“通话录音”，孤立文件检查接上。
- 导出归“聊天记录”（`BackupModule.CHATS`），zip 里加 `calls/`，`BackupFormat.mediaNamePattern` 加 `calls`；合并恢复时消息和联系人 id 重新映射、音频解压成新文件名。
- 按第四节第 7 条逐项检查 `CALL`：列表显示、会话预览、未读、通知、搜索、上下文、记忆总结、用量、删除和清空（含文件）、重试和重新生成、导出和恢复。

**数据**：`MessageType.CALL`、新表 `call_turn`、新目录 `files/calls/`；Room v8 → v9、备份内层 v8 → v9，旧消息和旧备份不受影响，0.7.2 打不开 v9 文件。

**请求内容回归**：不在通话时，聊天请求和 0.7.2 逐字一致（`ReplyRequestGoldenTest`）；另补通话中请求的基准。

**隐私**：通话的录音（只有说话的几段）发给这个联系人的语音识别来源，联系人的回复文字发给语音合成来源；本机来源不离开手机。新权限 `FOREGROUND_SERVICE_MICROPHONE`；VAD 模型随安装包，不另外下载。写进隐私草稿。

**测试**：只用本机模拟接口；录音、VAD、播放、编码和离线识别抽出接口，JVM 测试用假实现和预置音频。debug、perf 包用一段“说话—静音—说话”的预置音频代替麦克风；用手机麦克风、真机放出声音、调用真实服务商都先问用户。

**实施顺序**：数据与兼容 → 说话检测（单独提交）→ 通话流程（单独提交）→ 通话页、两个入口、权限、前台服务、音频焦点 → 通话消息和详情页 → 收尾（检查清单、门禁、设备端测试、升级和备份恢复、截图、文档、反向确认）。

**验收标准：**

- 两个入口都能发起通话；麦克风权限被拒时有说明和设置入口；这个联系人的识别或合成来源用不了时不能发起，并说明原因；
- 用户说完一段话后能转写并发给联系人，联系人的回复能按句合成、连续播放，之后接着听；静音、噪声、很长的一段话、“说完了”和“打断”的表现符合上面的规则；
- 识别、模型、合成失败和断网都有提示，通话不会卡死；连续失败、超时、长时间没人说话会自动挂断；挂断后没有残留的录音、播放、前台服务和请求；
- 通话不新开上下文，通话内容按条进入原聊天的上下文和记忆；不在通话时的聊天请求和 0.7.2 逐字一致；
- 通话消息显示时长和图标，点进去能看完整文字、播放完整音频和单条音频；
- 删除通话、删除联系人、清空聊天记录时音频文件同步删除；通话音频计入存储空间；导出和合并、覆盖恢复后通话记录、音频路径和联系人映射正确；
- 0.7.2 → 0.8.0 覆盖升级、0.7.2 的明文和整文件加密备份恢复都正确；
- 真实服务商、真机麦克风、真机放出声音的验证都先问用户，结果如实记录。

### 0.9.0 正式发布前的优化

**目标**：补齐消息操作和多语言，统一视觉和动画，为 1.0.0 做准备。

**1. 文本消息和语音消息**

- 多选后批量删除、复制（复制出的内容每条消息占一行）。
- 多选按消息 id 记录，配合分页；等待中和待投递的消息不能选。
- 批量删除同步删媒体文件并刷新会话预览；复制只复制文字（语音复制转写内容）。
- 长按消息可以收藏（收藏在“我”页可查）、引用（对选中的单条消息回复）、翻译（中文占比多则翻成英语，否则翻成中文）。
- 收藏要独立持久化并纳入备份，不能只存原消息 id，否则删除原消息后收藏会失效；具体删除原消息后的显示规则在实现前定清楚。
- 翻译使用用户已配置的模型，并计入用量；具体服务商和费用归属在实现前定清楚，不擅自新增收费调用。

**2. 通话消息**

- 多选后批量删除、复制（复制本通话完整内容）。
- 长按可以收藏；没有引用和翻译。

**3. App 图标和动画**

- App 图标定稿，并把剩余图标统一换成自绘线性风格。
- 对该 App 的页面转场、气泡和菜单等动画进行统一优化。
- 预测性返回：清单已开启，要改的是 `navigation/PageTransitions.kt` 中的 `PageFrame`。调整其 `BackHandler`，用 Navigation 自带预测性返回或 `PredictiveBackHandler` 让页面跟手，保留页面内部收键盘、关面板、放弃编辑的优先级。0.4.1 只核对过搜索页收键盘，不能代替整体回归；本版实现相关改动并验证受影响页面，完整手势与无障碍组合验收仍放 1.0.0。
- 气泡出现动画只对新到达的消息，分页加载历史时不能播；长按菜单弹出动画统一。

**4. 多语言**

- App 默认跟随系统语言，另有简体中文、繁体中文、英文可选。
