# 智信 AIChat 后续版本开发方向文档

适用范围：v0.3.1 之后至 v1.0.0 正式版
平台：Android 14+（minSdk 34，targetSdk 37），包名 isomeria.aichat，数据全部本地存储
更新于 2026-11-02。本版已对照 v0.3.1 源码（main `48b327a`）逐项核对，和原清单不同的地方见附录。

本文的产品取舍已全部定案（用户 2026-11-02 委托决定），开发时直接执行，不再逐项询问；实施中出现文档没有覆盖的实质问题时再问。

从 0.4.0 起这份文档在仓库里维护（`docs/roadmap.md`）。

路线是方向，不是开发授权。每个版本开工前仍以《智信 AIChat 工作交接》为准；真实服务商调用、操作正式版、改手机全局设置和 GitHub 发布，都要分别征得同意。

## 一、总体原则

1. **先底座，后功能。** 分页、崩溃日志这类基础能力越早有越好，所以放在最前面。
2. **先做被依赖的，后做依赖别人的。** 回复节奏引擎先于主动聊天和朋友圈；调度与费用额度先于朋友圈。
3. **独立且高风险的大模块放后面。** 语音要对接外部服务商，不确定性最高，后移可以避免卡住其他功能。
4. **叶子功能灵活安排。** 星标、多选、聊天背景没有别的功能依赖它们，可以随时插入任意版本。
5. **升级不改变已有联系人的行为和费用。** 这是 0.3.x 已经执行的规则。新能力默认作用于新联系人，已有联系人由用户主动开启。
6. **会自动花钱的功能默认关闭。** 没有用户操作就调用模型的功能，都要有开关、额度、用量归类和可见的运行状态。

## 二、现状基线

原清单写于不了解代码的情况下。下面这些已经存在，后续设计必须在此基础上改，不能当作从零开始。

| 能力 | v0.3.1 现状 | 对计划的影响 |
| --- | --- | --- |
| 分条显示 | `ReplySplitter` 按**空行**拆；联系人开关 `splitReplies`；同一轮共用 `replyGroup`；相隔 1 秒 | 0.5.0 是升级现有机制，不是新建 |
| 逐条出现 | 全部消息一次写库，时间写成未来；`ChatViewModel.revealed` 到点才显示 | 预览、未读、通知现在都是写库时一次完成，没有“待投递”状态 |
| 等待中又发消息 | `ReplyScheduler` 用 REPLACE 取消旧请求，新请求带上所有等待中的消息 | 生成前的插话已有规则，保留 |
| 上下文合并 | `ContextBuilder` 合并连续同角色消息，助手用 `\n\n` 连接 | 改拆条规则时要同步 |
| 时间和昵称 | 已写在系统提示词**末尾**。人设为空且没有记忆时，整段系统提示词不发送 | 0.5.0 不用新增时间注入 |
| 联系人记忆 | 按联系人保存，最多占预算 1/4；系统提示词也占预算 | 全局内容会挤占聊天记录 |
| 消息加载 | `observeByContact` 每次读整个聊天；重试、重新生成也读全部 | 0.4.0 分页要一起改 |
| 搜索定位 | 搜索结果用 `focusMessageId` 在全量列表里找位置 | 分页后要改成按消息定位 |
| 图片占位 | 已存宽高，气泡已按宽高固定尺寸 | 已完成，不用再做 |
| 媒体目录 | `files/images`、`files/avatars`，数据库和 MMKV 存**绝对路径**；图片已压到 2048 像素，不是原图 | 不搬目录 |
| 导出文件 | 只有 API Key 按密码加密；聊天内容和图片是明文 | 0.4.0 补全文件加密 |
| 恢复快照 | 恢复前写 `files/backups/before-restore.zip`，**成功后不删除**，界面也用不到 | 一份完整的数据副本一直留在手机上，0.4.0 改成成功后删除 |
| 本机数据保护 | 数据库、头像、聊天图片、MMKV 设置都靠系统的应用私有目录和全盘加密保护；只有 API Key 用 Keystore 单独加密 | 对外不能写成“数据已加密” |
| 系统备份 | `allowBackup=false` | 数据不会经系统备份离开手机 |
| 崩溃排查 | release 开启 R8，未保留行号，`mapping.txt` 未归档 | 崩溃日志必须一起解决 |
| 用量 | `usage_daily` 分 CHAT、MEMORY | 新用途要加分类 |
| 通知 | 第一次发消息时申请权限，点通知可进聊天；设置里已有“关闭电池优化” | 主动聊天复用 |
| 语音入口 | `ProviderKind` 已有 TTS、ASR；设置和输入栏有“即将支持” | 0.8.0 直接接上 |
| 预测性返回 | 清单已开启；`PageFrame` 的 `BackHandler` 会拦下，所以页面不跟手 | 0.9.0 要改的是这里 |
| App 图标 | 已有自适应图标和单色层，是自绘气泡 | 0.9.0 只做定稿复核 |
| 线性图标 | `WeIcons` 已有部分自绘，13 个文件仍在用 Material Icons | 0.9.0 替换完后删除依赖 |
| 硬编码文字 | strings.xml 共 507 条；Kotlin 里有 63 行中文字面量，多数是 Preview 和异常信息 | 0.9.0 前清理异常信息 |
| 测试 | 481 项 JVM 测试含截图，6 项设备端测试，lint 0 | 这是后续回归的起点 |

**已明确不做（用户决定，不要重新提出）：** 模型订阅和 OAuth 登录、Anthropic/Google 原生协议、OpenAI Responses、内置或联网模型目录、费用估算、OpenAI 品牌预置、任意请求 JSON 编辑器、语音通话（到 1.0.0 都不做）。

## 四、贯穿每个版本的开发规则

1. **数据库迁移。** 改表必须版本 +1、写 Migration、用 `app/schemas` 做迁移测试，禁止 `fallbackToDestructiveMigration`。数据只在本机，迁移失败就等于数据丢失。
2. **导出/恢复同步更新。** 新表、新字段、新设置和新媒体目录都要纳入。改 `data.json` 时 `BackupFormat.VERSION` +1 并补迁移。
   - 合并恢复时联系人 id 会变，新表里指向联系人的字段都要重新映射。
   - 新媒体目录要加进 `BackupFormat.mediaNamePattern`，否则恢复时会被当成非法路径。
   - 应随备份走的设置放进 `SettingsDto`，与设备有关的状态（如今日额度）不导出。
3. **文字资源。** 界面文字一律写进 strings.xml。Android lint 的 `HardcodedText` 只查布局 XML，管不到 Compose 的 `Text("…")`，把它设为 error 没有效果。改为加一个 JVM 守卫测试：扫描 `app/src/main/java` 里的中文字符串字面量，Preview 和注释除外，其余进白名单，只减不增。
4. **隐私说明草稿。** 每新增一个要连接的服务器或一类本地数据，就在 `docs/privacy-draft.md` 记一笔，1.0.0 时定稿。
5. **新页面图标。** 新页面需要的图标直接按 `WeIcons` 的自绘线性风格画。
6. **日志脱敏。** 任何日志都不得记录 API Key、消息正文、记忆、提示词和图片内容。**异常的 message 也算日志**，可能带着服务商返回内容或 URL，默认不写入崩溃日志。
7. **新消息类型或状态的检查清单。** 新增 `MessageType` 或 `MessageStatus` 时，逐项确认：列表显示、会话预览、未读、通知、搜索、上下文拼装、记忆总结、用量、删除和清空（含文件）、重试和重新生成、导出和恢复。
8. **自动调用模型的测试。** 只用本机模拟接口。真实服务商调用先问用户，debug 包里不放真实 Key 做调度测试。
9. **测试证据不进公开仓库。** `docs/audits`、`docs/validation` 含设备序列号、本机路径和过程记录，只留在本地分支；发布分支从 main 出发，保持干净。
10. **每次提交前。** `testDebugUnitTest lintDebug assembleDebug assembleRelease`；改页面时重录 Roborazzi 基线并看图，新页面补浅色和深色；改存储或迁移时跑 `connectedAndroidTest`。

## 五、各版本详细说明

### 0.4.0 稳定性与性能底座

**目标**：把分页做对，能看到崩溃原因，并堵上数据离开手机时的明文问题。后续每轮回复会变成多条消息，消息量会成倍增长。

**实施顺序**（一批一个提交，每批都能单独验证）：崩溃日志 → 分页 → 存储空间 → 导出加密和恢复快照。崩溃日志在前，后面几批出问题才看得到。

**本版不做数据库加密（用户决定，2026-11-02）。** 其他 App、关机后拆读和系统备份都已有保护，SQLCipher 多防的主要是 root 和离线取证，代价却是新增丢数据的路径、一次不可逆的迁移和更大的 APK。以后要做的话见第六节。

**1. 本地崩溃日志**

- `Thread.setDefaultUncaughtExceptionHandler` 捕获 Java/Kotlin 层崩溃，同步写入 `files/logs/`，然后**交还给原来的处理器**，不吞掉崩溃。
- 尽早安装：在 `Application.attachBaseContext` 或 `onCreate` 的 `super.onCreate()` 之前。Hilt 注入和数据库打开都可能崩。
- 启动时读 `ApplicationExitInfo`（minSdk 34 可直接用），只补记 ANR 和原生崩溃；记住已处理的时间戳，避免重复。
- 每条包含：时间、App 版本、设备型号、Android 版本、异常类名和堆栈。**默认不写异常 message**；ANR 的 trace 只留本 App 主线程，避免把其他内容带出去。
- 只保留最近 20 份。
- release 包的堆栈要读得懂：`proguard-rules.pro` 加 `-keepattributes SourceFile,LineNumberTable`，`release.yml` 把 `mapping.txt` 存为 CI 产物（约 50MB，不放进 Release 附件）。
- 设置 → 关于 → 崩溃日志：列表、单条查看、导出、清空。`file_paths.xml` 目前只开放了 cache，导出时先复制到缓存子目录再经 FileProvider 分享，不开放 `files/`。
- 日志页不依赖数据库，数据库出问题时也能看。
- 测试用的“触发崩溃”入口放在只进 `debug` 和 `perf` 的测试工具里，不能进 release 包（见下面“本地验证包”）。

**2. 聊天记录分页加载**

- 用 Paging 3 加 Room 的 PagingSource（新增 `androidx.paging`、`room-paging` 依赖），倒序，每页 30～50 条，预取 1 页。现有 `reverseLayout` 保留。
- 这些依赖全量列表的逻辑要一起改：
  - 时间条：`buildRows` 改成 `insertSeparators`。
  - “重新生成”：不再靠列表算最后一组，单独查询。
  - `retry()`、`regenerate()` 里的 `listByContact`：改成只查需要的范围，否则聊天越长越慢。
  - 列表 key 保持 `m{id}`，滚动位置不跳。
- **搜索定位不能丢**：从搜索进入时，先查比目标消息新的条数作为 `initialKey`，再定位和高亮。全局搜索和聊天内查找都要回归。
- 进入聊天定位到最新消息。有未读时定位到第一条未读：`onVisible()` 会立刻清零，要先取 `unreadCount` 再清；只标了红点（`markedUnread`）的没有数字，定位到最新。
- 停留在历史位置时收到新消息不跳走，显示“↓ N 条新消息”浮标，点击回到底部。自己发消息时总是回到底部（现有行为）。
- 图片占位已经实现，只回归，不重做。
- 万条测试数据由测试工具在 App 内生成（见下面“本地验证包”）。

**3. 媒体存储与缓存管理**

- **不搬现有目录。** 数据库和 MMKV 存的是绝对路径，搬目录要迁移路径、改备份逻辑，没有实际收益。现有 `files/images`、`files/avatars` 不动，以后按需新增同级目录：`files/moments`、`files/voice`、`files/background`，以及本版的 `files/logs`。
- **不做缩略图目录。** 聊天图片已压缩，Coil 按显示尺寸解码。万条测试如果确实卡，再加。
- 设置 → 数据 → 存储空间：聊天图片、头像、崩溃日志、缓存、数据库，各显示占用。计算在后台进行，先显示加载状态。
- “清理缓存”只删可再生内容：`cache/camera`、`cache/updates`、`cache/restore`、Coil 缓存。正在更新或恢复时不能删。
- 聊天图片只在删除对应消息时才删（现有行为）。
- “清理孤立文件”复用 `FileStorage.deleteUnreferenced`。注意它要包含联系人头像、自己的头像（在 MMKV）和消息图片；回复或恢复进行中不执行；先显示会删多少再确认。

**4. 导出加密和恢复快照（用户已确认）**

- 现状：只有 API Key 按密码加密，聊天内容和图片是明文。导出文件会离开手机，比如存进网盘或发给别人，这是最现实的泄露途径。
- 导出页改成一个可选的“设置密码”。设了密码就**加密整个文件**；“包含 API Key”必须设密码。
- 格式：外层加一个带魔数和版本的容器，分块 AES-256-GCM 流式加解密（图片可能很大，不能整体读进内存），密钥沿用 PBKDF2-SHA256 31 万次，盐每次随机。
  - 文件头作为 AAD 参与认证，参数被改就解不开。
  - 每块的 AAD 带序号和“是否最后一块”，**被截断、调换或拼接都要能发现**。只逐块 GCM 而不做这一步，截断的文件会被当成完整的。
  - nonce 不能在同一密钥下重复。
  - 内层仍是现有 zip，Key 继续用 `SecretDto` 的密码方案，内层格式保持 v3，恢复逻辑少改。
- 兼容：明文 zip 和只加密 Key 的旧备份继续能恢复。0.3.1 读不了加密文件，会提示文件损坏，需要写进更新说明。
- 恢复流程：先识别容器，要密码，错误时不改动任何数据。现有恢复用 `ZipFile` 读文件，要先解密成临时文件，这份明文放在 `cache/restore`，**恢复结束（成功或失败）立即删除，下次启动也清一遍**。
- 导出页写清楚：忘记密码无法恢复；卸载后只能靠导出文件恢复。
- `before-restore.zip`（恢复前的完整快照）改成**恢复成功后立即删除**，失败回滚的逻辑不变。

**本地验证包。** release 的包名就是正式版，不能装到手机上测。新增 `perf` 构建类型：和 release 相同的 R8 配置，包名 `isomeria.aichat.perf`，debug 签名，不 debuggable，不连 GitHub，不发布。测试工具（生成虚构消息、触发崩溃）只进 `debug` 和 `perf`。

**不改表。** 除非实施中确实需要，本版 Room 保持 v3，备份内层格式保持 v3。

**验收标准**

- 从 0.3.1 覆盖升级后数据完整，升级路径上没有任何数据迁移；
- 万条消息的聊天打开和滚动流畅，用 `perf` 包记录打开耗时和丢帧；搜索定位和未读定位正确；
- 人为制造崩溃后，`perf` 包能在设置里看到带行号的日志（能用 mapping 还原），日志里没有消息内容和 Key；
- 清理缓存后历史图片正常显示；清理孤立文件不误删；
- 加密导出可以恢复，错误密码不改动数据，被截断的文件被拒绝，旧备份仍能恢复；恢复成功后快照和解密临时文件已删除，恢复失败时仍能回滚；
- **首次真机验证正式签名的应用内升级**：发布后从手机上的 0.3.1 升到 0.4.0。这一步不可逆，要先问用户。

### 0.5.0 全局记忆、全局指令与回复节奏

**目标**：让所有联系人共享用户信息和基础人格准则，并让回复从“相隔 1 秒连发”变成像真人一样有节奏。这一版的核心是消息管线，不只是“我的”页多两个入口。

**1. 全局记忆**

- 入口：我 → 全局记忆。新表（条目、启用状态、排序、时间），纳入备份。
- 条目列表，每条可单独启用、编辑、删除。
- 显示总字数和大致 token。不同服务商估算系数不同（DeepSeek 汉字 0.6，其他 1），按较高的通用值显示。
- **要明确提示：这些内容会发给每个开启它的联系人所用的服务商。** 现有联系人记忆不跨服务商，全局记忆是第一次跨，不能悄悄发生。
- 本版只支持手写。自动提取列为未来功能。

**2. 全局指令**

- 入口：我 → 全局指令。分两部分：
  - **人格准则**：可编辑文本，内置默认内容，有“恢复默认”。
  - **回复节奏**：结构化参数（见第 3 项）。
- 首次安装时默认内容用中文，0.9.0 补英文。

默认人格准则草案：

```
你不是一个只会附和的助手，而是一个有自己性格的人。
- 你有自己的评判标准：同一件事，你会判断它好还是不好，并说出你的看法。
- 你有自己的边界：不是所有要求都会照单全收，不愿意的事可以拒绝。
- 你有自己的喜好：有偏爱的东西，也有不感兴趣的东西。
- 你的反应来自你的人格和经历，而不是只针对对方当前这一句话。
- 你可以不同意对方，也可以坚持自己的立场，不必事事顺着对方。
```

原草案最后一句“用换行分隔每一条”移到了节奏要求里。它是协议，不应放在可编辑、可关闭的文本中，否则关掉全局指令或改了文本，拆条就坏了。

**3. 回复节奏引擎**

参数（全局默认，联系人可覆盖）：
- 每条建议字数：14
- 每轮条数：2～5
- 去掉句尾标点：开
- 回复间隔：3～20 秒

**节奏要求由 App 生成。** 字数和条数写进提示词作为风格引导，协议（用换行分隔）也在这里；标点、拆条、间隔由 App 执行。这段文字随节奏开关走，和全局指令开关无关，计入预算。

**拆条规则：**
- 节奏开启时按任意换行拆，去掉空行。这样兼容已有人设模板里“用空行隔开”的写法（`prompt_template`），两种输出都能正确拆。
- 节奏关闭时沿用现有空行规则，已有联系人的行为不变。
- 条数超过上限时，把多出的尾部合并进最后一条。字数不做硬截断。
- 新联系人的 `prompt_template` 去掉“想分几条发时，用空行隔开”这句；不改写已有联系人保存的文本。
- 拼接历史时，节奏开启用 `\n` 合并同一轮，关闭仍用 `\n\n`。

**标点：** 只去掉每条末尾的“。”和“，”，保留“？”“！”“…”。在拆条时处理，存的就是显示的内容。

**间隔：** 按字数估算打字时长加少量随机，限制在设定范围内。第一条的等待要**扣掉模型已经用掉的时间**，否则真实等待会超过设定。时钟和随机数可注入，便于测试。

**投递可靠性（核心改动）：**
- 新增 `MessageStatus.PENDING`。模型返回后在一个事务里写入全部消息，`createdAt` 是计划时间，只用状态区分。枚举存文本，不需要改表结构。
- 只有转为 SUCCESS 时才更新会话预览、未读数和通知。现在是写库时一次完成，会提前剧透。
- 投递放在**单独的唯一任务** `deliver-{contactId}`。不能放在 `reply-{contactId}` 里，否则用户一发消息，REPLACE 就把投递也取消了。
- App 被杀后：启动时把到期的 PENDING 转为 SUCCESS，未到期的重新排队；`markInterruptedRequests` 不能把它们标成失败。任务重试时（`runAttemptCount > 0`）继续投递，不按失败处理。
- 通知：同一联系人的通知随投递更新，不要每条都响一次。
- “对方正在输入…”沿用 `typing`，等待回复或有 PENDING 时显示。

**用户插话：**
- 模型还没返回时，保持现有规则：取消旧请求，一起回。
- 投递期间又发消息：已生成的继续发完，新请求排在后面。`ReplyEngine.run` 要等 PENDING 全部投递后才开始。
- **这时用户消息的时间会夹在几条回复中间**，按时间拼接的话，发给模型的最后一条是助手消息，部分服务商会报错或接着往下写。拼接上下文时要把等待回复的用户消息排到最后。这一点要有回归测试。
- 用户点“取消”只取消还没生成的请求，不撤回 PENDING。删除聊天、清空、恢复要取消投递任务。

**按第四节第 7 条检查所有读消息的地方**，重点：
- 搜索不能搜到 PENDING；
- 记忆的 `planBatch` 现在只排除 SENDING，要把 PENDING 也排除；
- 导出时 PENDING 按已送达写入，恢复后不会再次投递；
- 聊天列表预览、重新生成（`typing` 时已禁用）。

**4. 提示词组装**

原清单把时间放在人设之前。有些服务商按相同前缀缓存计费（如 DeepSeek），时间每分钟都变，放前面会让后面全部失效，费用上升。现有实现放在末尾，继续保持。

组装顺序：
1. 全局人格准则
2. 全局记忆
3. 联系人人设
4. 联系人记忆
5. 节奏要求
6. 当前时间和昵称

- 全局和人设同时存在时写明：**联系人人设与全局准则冲突时，以联系人人设为准。**
- 全部为空时维持现有行为，不发送系统提示词。
- 只改 `ContextBuilder.systemPrompt` 一处。`MemoryEngine.historyBudget` 也调用它，触发阈值才会一致。
- 记忆总结和合并的请求（`labels.summaryPrompt`）**不带全局内容**，不增加费用，也不影响总结质量。

**预算：** 全局内容算进联系人的上下文预算。默认预算 4000，最小 1000。系统提示词太长时 `historyBudget` 会变成负数，聊天记录被丢光，记忆也会反复触发（有 200 的下限保护）。
- 不新增预算字段，不改 80%、1/4 的规则。
- 全局页和联系人编辑页显示占用。系统提示词超过联系人预算一半时，在联系人编辑页提示。
- 这种极端情况要有测试。

**5. 联系人设置**

- 新增：使用全局记忆、使用全局指令、回复节奏（跟随全局 / 自定义 / 关闭）。
- `splitReplies` 现有开关并入“回复节奏”，迁移时保留原值，不要出现两个互相矛盾的开关。
- 用途举例：设定了温顺随和的联系人，可以关掉“会坚持立场”的全局准则。
- **默认值：新联系人全开；0.5.0 之前的联系人全关，节奏为“关闭”。** 全局页提供“应用到全部联系人”。理由见总体原则第 5 条：全局内容每次请求都要花 token，升级后不能自动变贵或变性格。

**数据：** Room +1；备份 +1；旧备份迁移按“已有联系人”的默认值处理。

**验收标准**

- 新联系人不写任何人设也能读到全局记忆；关闭后读不到（看请求内容）；
- 回复分多条、带间隔出现，第一条的等待扣掉了生成时间；
- 投递中杀掉 App，重新打开后不丢、不重复、未读和预览正确；
- 投递中插话，发给模型的最后一条是用户消息；
- 关闭全局指令或节奏的联系人，请求内容和 0.4.0 一致（逐字段回归，含 DeepSeek 旧请求）；
- 已有联系人升级后请求内容不变；
- 全局内容很长时，聊天和记忆都不出错。

### 0.6.0 联系人主动聊天

**目标**：联系人根据时间和聊天状态主动来找用户。复用 0.5.0 的待投递机制；调度器和额度留给 0.7.0。这是第一个没有用户操作就花钱的功能，所以默认关闭，状态要看得见。

**1. 后台调度**

- WorkManager 周期任务，最小间隔 15 分钟，需要联网。只在至少一个联系人开启时才注册。
- 不用精确闹钟，不申请额外权限。App 回到前台时也检查一次（`lifecycle-process` 已有依赖）。
- **要接受的现实：** Android 的周期任务不准时，小米 HyperOS 还可能在划掉后台或省电时不执行，强制停止后要等下次打开才恢复。不能把“一定按时到”作为目标。设置页引导去关电池优化（已有入口）和开自启动，并显示最近运行时间。

**2. 触发逻辑**

- 对每个开启的联系人算触发概率：距上次互动、当前时段、频率设置。写成纯函数，时钟和随机数可注入。
- 这些情况直接跳过，不调模型：免打扰时段、超出活跃时段、今日额度用完、连续未回复已暂停、正在等回复或有 PENDING、用户此刻正在看这个聊天、配置校验不通过（`ModelRules.validate`）、没有 Key。
- 可能触发后调模型：人设、全局记忆、联系人记忆、最近聊天、当前时间，并说明“如果现在不想找对方，只输出 [SKIP]”。
- **请求结构：** 主动请求没有新的用户消息，历史可能以助手消息结束，甚至为空。要追加一条临时的 user 角色指令，只在这次请求里，不存库。
- **[SKIP] 判断要宽：** 去掉空白和标点后含有 SKIP 就不发。把 [SKIP] 显示给用户，比少发一条严重得多。
- 额度**在发请求前**扣减，[SKIP] 和失败都算。失败不重试，不通知。

**3. 设置项**

- 联系人级：
  - 主动聊天频率：关闭 / 偶尔 / 适中 / 频繁，默认关闭；
  - 活跃时间段：可选。
- 全局：
  - 免打扰时段，默认 23:00～8:00（要处理跨午夜）；
  - 每日主动调用上限，默认 20 次，0.7.0 的朋友圈调用也计入；按本地日期重置。
- 防刷屏：连续 2 次主动消息没回复就暂停该联系人，直到用户再次发言。
- 第一次开启时：申请通知权限（现在是第一次发消息时才申请，可能已被拒），并说明会自动消耗 API 额度。
- 状态显示：今日已用、最近运行时间、每个联系人是否暂停及原因。没有这些，用户无法区分“没触发”和“被系统杀了”。

**4. 消息和投递**

- 主动消息走 0.5.0 的节奏和投递，可以分多条，发系统通知，点击进入聊天（已有）。
- `Message` 加来源字段（普通回复 / 主动）。
- **主动消息不能“重新生成”。** 现有 `regenerate()` 删掉最后一轮回复后，会把前面的用户消息重发；没有用户消息时任务直接结束，这条主动消息就丢了。
- 记忆总结、上下文照常包含主动消息。现有逻辑会去掉开头的助手消息，主动消息不受影响；连续两轮助手消息会合并，要有测试。
- 用量新增 PROACTIVE 分类，用量页单独显示。

**数据：** Room +1（来源字段、联系人设置、会话的暂停状态、每日额度）；备份 +1。每日额度和暂停计数不随备份恢复。

**测试：** 只用模拟接口。debug 包提供“立即运行一次”。真机只用 debug 包，真实服务商的主动聊天先问用户。

**验收标准**

- 开启后用模拟接口能收到主动消息，分条、有通知、可点进聊天；
- 免打扰（含跨午夜）不调用模型；到达每日上限后不再调用，次日恢复；
- 连续未回复会暂停，回复后恢复；
- [SKIP] 不显示但计入额度；
- 主动消息没有“重新生成”，重试不会出错；
- 默认状态下没有任何后台模型调用；
- 真机杀进程、重启后的表现如实记录，不把 HyperOS 限制写成通过。

### 0.7.0 朋友圈

**目标**：仿微信朋友圈，包括用户发动态、AI 联系人发动态和互动。复用 0.6.0 的调度与额度、0.5.0 的投递。

**1. 数据模型**

- Moment：id、作者、文字、发布时间
- MomentImage：动态 id、路径、宽高、顺序
- Like：动态 id、点赞者、时间
- Comment：id、动态 id、作者、回复对象（可空）、文字、时间
- MomentTask：动态 id、联系人、到期时间、类型（待处理的互动）
- 作者字段用可空的联系人 id，**null 表示用户**。不要用 0：`usage_daily` 里 0 表示“已删除联系人”，容易混。外键级联：删除联系人时删掉它的动态和互动，同步删图片文件。

**2. 界面**（入口在“我”页）

- 顶部封面图（可更换，路径进备份）、自己的头像和昵称
- 动态倒序，分页加载
- 九宫格，点击大图（复用 `ImageViewerScreen`）
- 点赞区和评论区仿微信样式，不用微信的素材

**3. 用户发动态**

- 文字加最多 9 张图片，复用 `FileStorage` 的压缩和去 EXIF；可删除。
- 删除动态时同步删 `files/moments/` 下的图片，取消相关 MomentTask。

**4. AI 联系人发动态**

- 联系人级发布频率：关闭 / 每天 / 每周，默认关闭。
- 由 0.6.0 的调度器触发，提示词包含人设、近期聊天、当前日期，生成纯文字，允许 [SKIP]。
- 计入全局每日额度。AI 配图列为未来功能。

**5. AI 互动**

- **联系人级开关“参与朋友圈互动”，默认关闭。** 原清单默认每个联系人都排任务，用户发一条动态就可能花很多钱。
- “每条动态最多几个联系人互动”默认 3。
- 用户发动态后，为开启的联系人写入 MomentTask（随机几分钟到几小时），由调度器处理。不要每个联系人建一个 WorkManager 任务：取消、恢复、备份都更麻烦。15 分钟的粒度足够。
- 模型输出用简单标记（点赞 / 评论 + 文字 / [SKIP]），解析不了就当跳过，不用 JSON（部分服务商和模型不稳定）。
- 带图时，只有支持图片的模型才看图，其余只看文字。
- 用户回复评论后，该联系人接着回复，走延迟但不拆条。计入额度，额度用完就不回。
- 用量新增 MOMENTS 分类。联系人之间互评列为未来功能。

**6. 新动态提醒**

- “我”页入口显示红点或最新互动者的头像；底部“我”Tab 也要提示。用最后查看时间判断。

**7. 个人相册页**

- 点击头像查看该联系人或自己发过的动态。

**数据：** Room +1；备份 +1；新增 `moments/` 媒体目录；合并恢复时作者和联系人 id 要重新映射；MomentTask 不备份。

**聊天不带朋友圈内容。** 本版聊天请求不加入动态和评论，避免每次请求都变贵；以后要做见第六节。

**验收标准**

- 默认状态没有任何朋友圈相关的模型调用；
- AI 动态按频率出现且计入额度；开启互动后用户发动态能收到点赞或评论；
- 回复评论能收到后续回复；额度用完后停止；
- 删除动态、删除联系人后图片文件同步删除，任务取消；
- 导出和合并恢复后作者、评论对象正确。

### 0.8.0 语音聊天

**目标**：支持语音消息的收发，语音条样式仿微信。不实现语音通话。

**1. 语音服务配置**

- 抽象 TtsProvider、AsrProvider 接口，先实现 OpenAI 兼容格式（`/audio/speech`、`/audio/transcriptions`），其他以后按需加。
- 不内置音色目录：可手动输入音色 id，接口有列表时才显示列表。

**2. 联系人音色**

- 可单独选音色，不选用全局默认。

**3. 按住说话**

- 输入栏已有语音切换按钮，接上现有入口。第一次使用时申请 `RECORD_AUDIO`，拒绝后有说明和设置入口。
- 按住录音，上滑取消，松开发送。提供无障碍可用的替代操作（点一下开始、再点结束），长按手势读屏用不了。
- 短于 1 秒提示“说话时间太短”，最长 60 秒。

**4. 语音条样式**

- 自己绿色、对方白色；宽度随时长增加；显示时长；播放时有声波动画。
- 长按菜单有“转文字”。
- 连续多条未播放的，点击第一条后依次播放。
- 处理音频焦点：来电或其他 App 播放时暂停。

**5. AI 回复方式**

- 联系人级：文字 / 语音 / 跟随我。默认文字。
- 语音回复时，拆出的多条合并成 1～2 条较长的语音。
- 先生成文字、再调 TTS，文字存库，“转文字”直接显示。
- TTS 成功后才进入 0.5.0 的待投递。
- TTS 失败时降级为文字消息，不重复请求模型。

**6. 按第四节第 7 条检查 VOICE 类型**

重点：会话预览“[语音]”；上下文用转写文字；`deleteMessage`、`deleteConversation`、`clearHistory` 现在只处理 `imagePath`，要带上语音文件；孤立文件清理、存储空间统计；备份 +1，新增 `voice/` 目录（现有单文件上限 64MB 够用）；搜索包含转写（现在只查 TEXT，要改）；用量：TTS 和 ASR 不是按 token 计，新增分类时不要混进现有统计。

**7. 隐私和测试**

- 录音会发给用户配置的 ASR 服务商，首次开启时说明，写进隐私草稿。
- 真机测试用预置音频，不录用户手机周围的声音；要用麦克风先问用户。

**验收标准**

- 录音的发送与取消都正常；被拒绝权限时有提示；
- 语音被正确识别并获得回复（模拟接口）；

- 删除消息后语音文件同步删除；语音文件计入存储空间统计，随备份恢复；
- 真实 TTS/ASR 服务商的验证，先问用户，结果如实记录。

**数据库加密的启用条件和备忘。** 2026-11-02 从 0.4.0 移出。手机可能被 root，或者想公开承诺“数据库已加密”时再做。它不改表结构，晚做的代价主要是迁移耗时更长。要做的话，这些是已经查明的要点：

- 依赖 `net.zetetic:sqlcipher-android`（2026-11 官方最新 4.20.0）加 `androidx.sqlite:sqlite`，用 `SupportOpenHelperFactory` 接入 Room 2，打开前 `System.loadLibrary("sqlcipher")`。不要用已停更的 `android-database-sqlcipher`。
- 密钥用 Keystore 里单独的别名加密，密文存 `noBackupFilesDir`。
- 迁移要有进程级闸门（`AIChatApp.onCreate` 会查库，WorkManager 也可能先拉起进程），不在主线程。
- 先 `wal_checkpoint`。`sqlcipher_export` 不修改目标库的 `user_version`，要手动设置并校验。每一步被杀都能恢复；失败保留明文库。
- 密钥失效时不能自动建空库，要有恢复页。
- 现有的 `adb push` 写库测试方式会失效，要先做调试工具。

**补上的遗漏和风险**

- 崩溃日志：release 没有行号、mapping 没归档；异常 message 可能带隐私；安装时机。
- 数据离开手机：导出文件明文；`before-restore.zip` 一直留着。
- 分页：搜索定位、时间条、重新生成、未读计数被提前清零。
- 投递：独立任务（否则被 REPLACE 取消）、预览和通知提前剧透、插话后最后一条不是用户消息、记忆和搜索要排除待投递。
- 全局内容：挤占预算、跨服务商发送、费用、时间放前面破坏前缀缓存。
- 主动聊天：请求结尾不是用户消息、“重新生成”会弄丢主动消息、HyperOS 现实、状态可见。
- 朋友圈：互动默认关闭、联系人删除级联、合并恢复映射 id、任务存表。
- 语音：删除和清理现在只认 `imagePath`、备份路径白名单、麦克风测试隐私。
- 英文化：提示词也会被翻译、中文模板的占位判断。
- 1.0.0：TalkBack、字体 2.0、手势返回、七家真实服务商都已排入；隐私说明不能写成“数据已加密”。
